## 1. Executive Summary

A user received an email that appeared to come from **Banco Bradesco**, one of Brazil's largest banks. It said that **92,990 Livelo reward points would expire today** and urged the reader to click **"Resgatar Agora"** ("Redeem Now"). Both links in the message lead to `blog1seguimentmydomaine2bra[.]me`, a domain unrelated to the bank, which is almost certainly a page built to collect banking credentials or card details.

The message **failed every email authentication check** (SPF, DKIM, DMARC and Microsoft's composite authentication). It was sent as the Linux `root` user from a throwaway **DigitalOcean** cloud server that still had its default hostname. Microsoft 365 rated it as spam, but it **was still delivered to the Inbox** because of an entry on the user's **Trusted Senders** list. That override is the main control failure in this incident.

## 2. Detection

**No automated alert led to this investigation.** The analyst reviewed the reported message manually. The mail platform did spot the threat: it gave the message a Spam Confidence Level of 5 and a Bulk Complaint Level of 9. A user-level allow list then overrode that verdict (Section 5). In a production SOC this type of case usually starts with a **user report** (the "Report Phishing" button) or a **post-delivery spam verdict** that a user setting overrode.

## 4. Investigation and Analysis

### 4.1 Sender identity

| Header | Value | Assessment |
|---|---|---|
| From (display) | `BANCO DO BRADESCO LIVELO` | Brand impersonation |
| From (address) | `banco.bradesco@atendimento.com.br` | *Atendimento* means "customer service". This is a generic domain, not `bradesco.com.br` or `livelo.com.br` |
| Return-Path | `root@ubuntu-s-1vcpu-1gb-35gb-intel-sfo3-06` | Doesn't match From. The envelope sender is the `root` user of a bare server |
| Message-ID | `<20230919183549.39DEA3F725@ubuntu-s-1vcpu-1gb-35gb-intel-sfo3-06>` | Generated by the same server, not by a bank's mail system |

**The sending server.** The hostname `ubuntu-s-1vcpu-1gb-35gb-intel-sfo3-06` follows DigitalOcean's default droplet naming (Ubuntu, the 1 vCPU / 1 GB plan, the San Francisco 3 region). An ARIN RDAP lookup on **137.184.34.4** returns the network `DIGITALOCEAN-137-184-0-0` (137.184.0.0/16), which confirms the hosting provider. A bank doesn't send customer mail from a cheapest-tier VPS as `root`.

### 4.2 Authentication

```
spf=temperror  (sender IP is 137.184.34.4) smtp.mailfrom=ubuntu-s-1vcpu-1gb-35gb-intel-sfo3-06
dkim=none      (message not signed)
dmarc=temperror action=none header.from=atendimento.com.br
compauth=fail  reason=001
```

- **SPF temperror:** the envelope domain is a bare hostname with no DNS records, so SPF can't be evaluated.
- **DKIM none:** the message isn't signed. A real bank's mail is signed.
- **DMARC temperror:** there is no aligned SPF or DKIM pass for `atendimento.com.br`.
- **compauth fail (reason 001):** Microsoft's combined check concluded the sender isn't who the From header claims.

### 4.3 Message body

The body is a single base64-encoded `text/html` part titled *"Pontos Livelo"*. Translated summary:

> "You have Livelo Points on your Bradesco card available to redeem that **expire TODAY**. Avoid losing these points by redeeming your Visa Infinite score **right now**… **92,990 POINTS ACCUMULATED: EXPIRE TODAY.** [Redeem Now]"

| Social-engineering technique | Evidence |
|---|---|
| Urgency / deadline | "expiram HOJE", "expirando hoje", "agora mesmo", "antes que eles expirem" |
| Fear of loss | "evite a perda destes pontos" (avoid losing these points) |
| Reward / greed | A large, specific balance (92,990), airline miles, "up to 35% off" |
| Authority | Bradesco + Livelo + "Visa Infinite" + "CLIENTE PRIME" in the subject |

### 4.4 Links

| Visible text | Real destination |
|---|---|
| "Clique aqui" (in a fake "click to see images" banner) | `hxxps://blog1seguimentmydomaine2bra[.]me/` |
| "Resgatar Agora" (main button) | `hxxps://blog1seguimentmydomaine2bra[.]me/` |

Both clickable elements go to the same off-brand domain. The landing page was **not visited**. Its purpose (a fake login or card-data form) is inferred from the lure and is common for this campaign type, but this investigation didn't confirm it.

### 4.5 Other artifacts

- **Relative image paths** (`header.png`, `icone-superior.png`, `icone-rodape.png`). The HTML was copied from a web page, so the images won't load in an email client. It's a sloppy build, typical of mass phishing kits.
- **No attachments.**

### 4.7 Scoping (what a production SOC would run)

The dataset contains only the email itself, so it can't show whether the user clicked or whether other users received it. In a real environment the next step is to scope with mail and proxy logs. Example Splunk searches:

```spl
index=email (sender_domain="atendimento.com.br" OR src_ip="137.184.34.4"
  OR subject="*BRADESCO LIVELO*")
| stats count values(recipient) AS recipients by subject, sender
```

```spl
index=proxy url="*blog1seguimentmydomaine2bra.me*"
| stats earliest(_time) AS first_visit count by user, src_ip, http_method
```

A **POST** request to the landing domain would mean the user submitted data there, which raises severity to High and triggers credential reset.

## 5. Why the Existing Controls Missed It

The mail platform **detected** the threat but **did not block** it:

```
X-MS-Exchange-Organization-SCL: 5
X-Microsoft-Antispam: BCL:9;
X-Microsoft-Antispam-Mailbox-Delivery: ... dest:I; OFR:TrustedSenderList; ...
```

- **SCL 5** normally sends a message to Junk.
- **`OFR:TrustedSenderList`** shows the filtering verdict was overridden by the user's **Safe/Trusted Senders** list, and **`dest:I`** shows it went to the **Inbox**.

So a user-controlled setting beat an organization-level spam verdict, even for a message that failed composite authentication. This is the root control gap (Section 8).

## 8. Root Cause

A spoofed message from an unauthenticated cloud server reached the user's Inbox because the **user's Trusted Senders list overrode the platform's spam verdict**. The organization also had no policy that quarantines messages failing composite authentication (`compauth=fail`) regardless of user settings. The attacker needed no technical exploit. The attack relied on social engineering (urgency and a reward) and on that allow-list gap.

## 9. Containment and Remediation

| Step | Action | Status |
|---|---|---|
| Contain | Purge the message from every mailbox (search by Message-ID and subject) | **Recommended** |
| Contain | Block `blog1seguimentmydomaine2bra[.]me` at the DNS filter / web proxy | **Recommended** |
| Contain | Block the sender domain `atendimento.com.br` and IP `137.184.34.4` at the mail gateway | **Recommended** |
| Investigate | Run the proxy search in 4.7. For any user with a POST to the landing domain, reset credentials and tell them to contact their bank about card data | **Recommended** |
| Report | Report the droplet to DigitalOcean abuse and the domain to its registrar | **Recommended** |
| Harden | Remove the broad Trusted Senders entry that allowed delivery | **Recommended** |

This is public practice data with no live environment behind it, so the actions above are what a real response would do. None were carried out.

## 10. Recommendations and Lessons Learned

**Detection**
- Alert when a message is delivered to the Inbox **despite** `compauth=fail` or SCL ≥ 5 (an allow-list override). That combination is rare for real mail and worth reviewing.
- Alert on mail whose originating `Received` hop is a default cloud-VPS hostname and whose Return-Path is `root@`.
- Correlate mail delivery with proxy logs so that a click on a newly seen domain from a flagged email raises a case automatically.

**Email security configuration**
- In Microsoft Defender for Office 365, turn on "honor DMARC policy" and set spoof/compauth failures to **quarantine**.
- Limit or audit users' Safe/Trusted Senders lists. Don't let them override authentication failures.

**User awareness**
- Train users on **reward/points-expiry** lures, which are a common theme in Brazilian banking phishing. Real banks don't threaten to "expire" points within hours by email.
- Teach users to hover over buttons and compare the real domain with the brand.

**Lessons learned**
- **Read the headers, not the display name.** Every decisive clue was in the headers: the `root@` Return-Path, the VPS hostname, the failed authentication and the allow-list override.
- **Detection isn't prevention.** The platform scored this message correctly, and a user setting still delivered it. Check what overrides your controls, not only what the controls catch.
- **Static analysis is enough for a verdict.** This case was confirmed without opening the link, which keeps the analyst and the analysis machine safe.
